## Cover letter

```
net: mdio: add timestamped MDIO writes for PHY gettimex64
```

Draft for v2 (v1 as sent is `../v1/0000-cover-letter.patch`). Figures are v1's: recheck them
with a v2 build (#20); the 300 ns PHY margin widens the brackets by 0.3 µs.

Recipients for v2 (#23), in addition to v1's: Andrew Lunn <andrew@lunn.ch> (as well as
andrew+netdev@lunn.ch), Vladimir Oltean <olteanv@gmail.com>, Hubert Feurstein

```
PTP_SYS_OFFSET_EXTENDED uses gettimex64 to bracket each PHC read with
system clock reads. Some PHYs have a PTP hardware clock (PHC) that is
read over MDIO and sometimes multiple MDIO transfers are needed to read
the clock. This leads to brackets in the tens of microseconds.
Applications that synchronize the system clock from the PHC typically
use the midpoint of the bracket as the system time of the PHC reading.
With multiple transfers, the midpoint of the bracket is typically far
from the time when the PHC reading actually occurred.

For example, using PTP_SYS_OFFSET_EXTENDED on the Raspberry Pi CM5 to
synchronize the system clock from the BCM54210PE PHY PHC leads to the
system clock being 32 µs ahead of the PHC. On the CM4, it is about 7 µs.
(The difference is because the MDIO clock frequency is higher on the
CM4: 10 MHz as opposed to 2.08 MHz on the CM5.) The brackets are about
74 µs on the CM5 and 42 µs on the CM4. In comparison, the MAC PHC
on the CM5 has brackets of about 1 µs.

This series introduces a new MDIO operation, write_sts, that allows a
PHY driver to ask the MDIO bus driver for system timestamps bounding
the completion of a clause 22 MDIO write transfer. A bus driver
computes them by shifting the timestamps taken around the start of the
transfer by bounds on its duration, worked out from the MDC period and
the length of the frame. The series:

- adds the operation to the MDIO core;
- adds ktime_scale_raw_ns() to timekeeping, and ptp helpers that use it
  to shift system timestamps by a CLOCK_MONOTONIC_RAW duration;
- makes bcm-phy-ptp use the operation for the write that triggers the
  capture of the PHC time, allowing 300 ns for the PHY to capture it;
- implements the operation for macb, on RP1 only, where its timing has
  been measured;
- implements it for UniMAC, when the mdio node has a clock giving the
  MDC reference rate. On BCM2711 that is the GISB clock, which Nicolai
  Buchwitz is adding to clk-bcm2835 [1]. Until then BCM2711 does not
  get write_sts, and nothing changes.

The effect of this series is to reduce PTP_SYS_OFFSET_EXTENDED brackets
from 74 µs to about 1.3 µs on the CM5, and from 42 µs to about 0.9 µs on
the CM4. The synchronization error drops from 32 µs and 7 µs to tenths
of microseconds, below the level that can be reliably measured with the
methods below.

SPI introduced a similar facility to allow a device driver to obtain
timestamp bounds from the bus controller in commit 79591b7db21d ("spi:
Add a PTP system timestamp to the transfer structure"). This series
implements the operation for only one PHY driver. But I surveyed other
PHY drivers and identified at least two for which this operation could
be implemented: micrel (specifically LAN8814) and dp83640, although
they would need updating to use gettimex64 first.

Prior art
---------

A discussion in 2019 dealt with the same problem for the PHC of
mv88e6xxx switches [2]: the PHC is read over MDIO with several
transfers, and one write fixes the moment at which the clock is
sampled. Richard and Andrew suggested taking the system timestamps in
the MDIO bus driver, around that write, and Hubert Feurstein posted a
series implementing this [3][4][5]. This series settles the points
raised there. The timestamps bound the end of the write transfer. The
bus driver shifts the lower and upper timestamps by separate bounds on
the transfer time, measured on hardware, so the result is guaranteed
to contain the end of the transfer (Miroslav). The bus drivers take
the timestamps with local interrupts disabled, and flush the posted
write before taking the upper timestamp (Vladimir). And the PHY driver
allows for the delay between the end of the transfer and the PHY
capturing its time.

It differs in having a write_sts operation, rather than an sts pointer
in struct mii_bus. This allows the bus driver to compute the bounds at
each call, from the same divider and clock rate that it uses to set the
MDC speed. There is no fallback in the core, because a bus driver's
write may return before the transfer has completed.

Measurement
-----------

On both boards, the same PPS signal from a GPS receiver goes to the
PHY's SYNC pin and to GPIO 18 (header pin 12), and the PHC is
synchronized to it from the SYNC pin captures. The system time of each
pulse is measured by polling the GPIO register with ppsbias
(https://github.com/jclark/ppsbias), and compared with the system time
that PTP_SYS_OFFSET_EXTENDED gives for the same PHC time. On the CM4
the GPIO is on-chip, so a poll takes about 0.15 µs and the polling
error is under 0.1 µs. On the CM5 the GPIO is on RP1, across PCIe, so
the measurement is less precise there.

On the CM5 the MAC PHC gives a second check. /dev/ptp1 is the macb PHC,
whose PTP_SYS_OFFSET_EXTENDED brackets are about 1 µs since commit
9ca4ba242591 ("net: macb: fix ordering around PTP timestamp read").
With /dev/ptp1 synchronized to a PTP grandmaster and the system clock
synchronized from it, the offset between the system clock and the
result of PTP_SYS_OFFSET_EXTENDED on the BCM54210PE PHC agrees with
ppsbias.
```

## Commit messages

### 1/5

```
net: mdio: add timestamped write operation

Add an optional write_sts bus operation returning system timestamp
bounds for completion of a clause 22 MDIO write. This allows PHY
drivers to obtain tighter bounds when implementing gettimex64. SPI
introduced a similar facility to allow a device driver to obtain
timestamp bounds from the bus controller in commit 79591b7db21d ("spi:
Add a PTP system timestamp to the transfer structure").

The core provides no fallback, because a bus driver's write may return
before the transfer has completed.

An aux clock that is disabled and re-enabled restarts its raw time
with the same clock_was_set_seq, so the core cannot always tell that
the clock was reset during a write. Such a reset can fall within any
PTP_SYS_OFFSET_EXTENDED sample, whatever the driver, and
ptp_sys_offset_extended() does not check for it, so detecting it is
left to the PTP core. The MDIO core only caps its wait for the upper
bound, so that a reset cannot make it spin.

Also add MDIO_C22_FRAME_BITS and MDIO_PREAMBLE_BITS, the lengths of a
clause 22 frame and of its preamble, for bus drivers that work out
from the MDC period when a write completes.

Signed-off-by: James Clark <jjc@jclark.com>
Assisted-by: LLM
```

### 2/5

```
net: phy: broadcom: use timestamped MDIO writes in gettimex64

When the MDIO bus provides the write_sts operation, use
__phy_write_sts() to obtain tighter system timestamp bounds in
gettimex64 by timestamping completion of the write that triggers
capture of the PHC time.

The PHY captures its time a short delay after the last MDC edge of the
write, so add 300 ns to the upper bound. On a Raspberry Pi CM4, with
the same PPS signal on the PHY's SYNC pin and on GPIO 18, the PHC was
read with PTP_SYS_OFFSET_EXTENDED while the system time of each pulse
was measured by polling the GPIO. No capture out of 14,184 fell past
the upper bound, and the delay was at most about 0.34 us.

This patch does not try to fix the error handling in the existing
framesync code, which ignores MDIO write errors.

Signed-off-by: James Clark <jjc@jclark.com>
Assisted-by: LLM
```

### new in v2, before 3/5

```
timekeeping: add ktime_scale_raw_ns()

Add ktime_scale_raw_ns(), which scales a duration in monotonic raw
time by the frequency of a given clock relative to monotonic raw, as
set by that clock's current frequency correction.

The ptp helpers added in the next patch shift the system timestamps
taken by ktime_get_snapshot_id() by a duration measured in monotonic
raw time. To shift the selected clock's time by the same interval, the
duration has to be scaled by that clock's frequency relative to
monotonic raw.

Scale by tkr_mono.mult / tkr_raw.mult of the clock's timekeeper, as
adjust_historical_crosststamp() does. For an AUX clock this is the AUX
clock's own timekeeper.

Signed-off-by: James Clark <jjc@jclark.com>
Assisted-by: LLM
```

### 3/5

```
ptp: add functions to adjust system timestamps

Add ptp_adjust_system_prets() and ptp_adjust_system_postts(), which
shift the pre or post system timestamp by a given CLOCK_MONOTONIC_RAW
duration. The selected clock's time is shifted by the duration scaled
by that clock's frequency relative to CLOCK_MONOTONIC_RAW, with
ktime_scale_raw_ns().

An MDIO bus driver can take system timestamps around the command that
starts a write, and knows how long after that command the write
completes, so it can shift the timestamps to bound the completion of
the write.

Signed-off-by: James Clark <jjc@jclark.com>
Assisted-by: LLM
```

### 4/5

```
net: macb: implement timestamped MDIO writes

Implement write_sts to provide system timestamp bounds for completion
of an MDIO write. This enables tighter system timestamp bounds in PHY
implementations of gettimex64.

Take system timestamps around the command register write, then add
the time from the command write until the MDC edge that clocks the
last data bit, calculated from the peripheral clock rate and the
configured MDC divider.

On RP1 that edge comes 63.5 MDC periods after the command write, half
a period before the end of the 64-bit frame. This was measured on a Raspberry Pi CM5 with its BCM54210PE PHY. The PHY's
PHC was read with PTP_SYS_OFFSET_EXTENDED while the MDC divisor was
switched between 48 and 128 through /dev/mem. Any error in the number
of periods would make the PHC offset jump at each switch. After
compensating for drift, the jump with 63.5 periods was under 2 ns.
The MDC divider does not appear to run freely: the spread of the PHC
offsets did not change with the divisor.

Enable write_sts only where the delay has been measured, with a new
MACB_CAPS_MDIO_WRITE_STS capability that only RP1 sets for now. Other
platforms can set it once the delay has been measured on them. RP1's
pclk is clk_sys, whose rate is set by assigned-clock-rates and does
not change, so read the rate once at probe.

Signed-off-by: James Clark <jjc@jclark.com>
Assisted-by: LLM
```

### 5/5

```
net: mdio: bcm-unimac: implement timestamped MDIO writes

Implement write_sts to provide system timestamp bounds for completion
of an MDIO write. This enables tighter system timestamp bounds in PHY
implementations of gettimex64.

Take system timestamps around the command start, then add the time
from the command start until the MDC edge that clocks the last data
bit, calculated from the reference clock rate and the configured MDC
divider.

The edge comes half an MDC period before the end of the 64-bit frame,
or of the 32-bit frame when the preamble is suppressed. On BCM2711 the
MDC divider runs freely, so the frame starts up to one period after
the command start, and the edge comes 63.5 to 64.5 periods after it.
This was measured on a Raspberry Pi CM4 with its BCM54210PE PHY. The
PHY's PHC was read with PTP_SYS_OFFSET_EXTENDED while the MDC divider
field was switched between 9 and 39 through /dev/mem. The delay grew
by 640 ns for each step of the divider field, which is 64 periods of
the 200 MHz reference clock: with 64 periods, the jump in the PHC
offset at each switch was under 10 ns after compensating for drift.
The PHC offsets spread evenly over one MDC period at each divider. A
UniMAC whose divider restarted with the command would put the edge at
63.5 periods, still within these bounds. The frame without preamble
has not been measured.

Take the reference rate from a clock on the mdio node, and offer
write_sts only when there is one. When GENET creates the UniMAC
device, the clock it passes is its own main clock, which gates
register access but is not the MDC reference. No in-tree DT gives an
mdio node a clock yet. For BCM2711, the GISB clock, which MDC is
divided from, is being added to clk-bcm2835 separately.

Signed-off-by: James Clark <jjc@jclark.com>
Assisted-by: LLM
```
